title: Architecture
description: How the API, relay, clients, and storage fit together.
---

The control plane is a Go service backed by PostgreSQL for durable state and
Redis for ephemeral presence, heartbeats, rate limits, and relay coordination.
The relay is a separate Go process responsible for public ingress and live
stream forwarding.

```text
CLI or SDK ── HTTPS ──> API ── control state ──> PostgreSQL
     │                   │
     └── WebSocket ───> Relay ── ephemeral state ──> Redis
```

The web and desktop applications are clients of the same public API. They do
not bypass organization authorization or relay session authentication.

## Responsibilities

The API owns identity, organizations, billing, tunnel metadata, hostname
allocation, audit events, and durable usage records. PostgreSQL is the source
of truth for those records.

The relay owns live WebSocket sessions, hostname routing, stream forwarding,
backpressure, connection limits, and relay metrics. Redis coordinates ephemeral
presence, heartbeats, rate limits, and relay affinity; it is not a payload
store.

The CLI and SDK authenticate before opening a relay session. The desktop app
uses the same client behavior through the Tauri bridge, so desktop and CLI
connections have the same authorization and plan enforcement.
